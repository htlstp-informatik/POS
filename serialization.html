Java Serialization

Objekte speichern und wiederherstellen

Was ist Serialisierung?

Serialisierung wandelt den Zustand eines Java-Objekts in eine Bytefolge um. Deserialisierung stellt daraus ein Objekt wieder her. Anwendungen sind Dateien, Netzwerkübertragung und Kommunikation zwischen Programmen.

Objekt → ObjectOutputStream → Bytefolge → ObjectInputStream → Objekt

Die Datei enthält Daten und Klasseninformationen, aber nicht den Java-Quellcode oder die Implementierung der Methoden. Die passende Klasse muss beim Einlesen verfügbar sein.

Grundlagen und Methoden

Warum nicht einfach DataOutputStream?

Mit DataOutputStream müssen wir jedes Feld selbst schreiben und in derselben Reihenfolge lesen. Bei referenzierten Objekten müssen wir auch deren Format festlegen. Das folgende Beispiel speichert einen Namen und ein Alter manuell.

try (DataOutputStream out = new DataOutputStream(new FileOutputStream("manual.bin"))) {
    out.writeUTF("Anna");
    out.writeInt(25);
}
try (DataInputStream in = new DataInputStream(new FileInputStream("manual.bin"))) {
    System.out.println(in.readUTF()); // Anna
    System.out.println(in.readInt()); // 25
}

Bei einer Adresse müssten weitere Felder in einer vereinbarten Reihenfolge folgen. writeUTF enthält eine Längenangabe; readAllBytes wäre hier ungeeignet, wenn danach noch andere Felder folgen. Java-Serialisierung übernimmt die Verwaltung des Objektgraphen.

Serializable – Marker-Interface

Serializable aus java.io enthält keine Methoden. Die Klasse signalisiert damit, dass ihre Instanzen durch die Java-Objektserialisierung gespeichert werden dürfen. Ohne diese Kennzeichnung führt writeObject bei einem gewöhnlichen nicht serialisierbaren Objekt zu einer NotSerializableException.

import java.io.*;

class Person implements Serializable {
    @Serial
    private static final long serialVersionUID = 1L;
    String name;
    int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
}

ObjectOutputStream und ObjectInputStream

Der ObjectOutputStream umwickelt einen OutputStream, der die Bytes zum Ziel transportiert. Sein Konstruktor schreibt bereits einen Stream-Header. ObjectInputStream liest und prüft diesen Header beim Erzeugen. Ein leerer oder falscher Stream kann daher bereits beim Konstruktor eine Exception auslösen.

// In main mit throws IOException, ClassNotFoundException
Person p = new Person("Anna", 25);
try (FileOutputStream fos = new FileOutputStream("person.ser");
     ObjectOutputStream out = new ObjectOutputStream(fos)) {
    out.writeObject(p);
}
try (FileInputStream fis = new FileInputStream("person.ser");
     ObjectInputStream in = new ObjectInputStream(fis)) {
    Person loaded = (Person) in.readObject();
    System.out.println(loaded.name); // Anna
    System.out.println(loaded.age);  // 25
    System.out.println(p == loaded); // false
}

writeObject(Object) schreibt den Zustand des Objekts und seiner serialisierbaren Referenzen. readObject() liefert Object, weil der Stream verschiedene Klassen enthalten kann. Der Cast zu Person ist nötig, um Person-Felder zu verwenden; bei einem falschen Typ entsteht eine ClassCastException. ClassNotFoundException bedeutet, dass eine benötigte Klasse nicht geladen werden konnte. IOException signalisiert etwa beschädigte Daten oder I/O-Fehler.

Methoden im Überblick

reset(): Warum wird ein verändertes Objekt nicht erneut gespeichert?

Der Stream merkt sich bereits geschriebene Objekte anhand ihrer Identität. Beim zweiten writeObject mit derselben Referenz schreibt er normalerweise nur einen Verweis auf das erste Objekt. Das spart Platz und erhält gemeinsame Referenzen. reset() löscht diese Zuordnung, nicht die bisherigen Dateidaten.

Person p = new Person("Anna", 25);
try (ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("reset.ser"))) {
    out.writeObject(p);
    p.age = 30;
    out.writeObject(p); // nur Referenz auf das erste Objekt
    out.reset();
    out.writeObject(p); // neuer Zustand
}
try (ObjectInputStream in = new ObjectInputStream(new FileInputStream("reset.ser"))) {
    Person a = (Person) in.readObject();
    Person b = (Person) in.readObject();
    Person c = (Person) in.readObject();
    System.out.println(a.age); // 25
    System.out.println(b.age); // 25
    System.out.println(c.age); // 30
    System.out.println(a == b); // true
    System.out.println(a == c); // false
}

reset ist nicht mit InputStream.reset zu verwechseln: Es springt nicht zu einer früheren Position. Beim Lesen werden die Referenztabellen an der Reset-Markierung ebenfalls zurückgesetzt. Mehrere Objekte sollten mit demselben ObjectOutputStream geschrieben werden; einfaches Anhängen mit einem neuen ObjectOutputStream erzeugt einen zusätzlichen Header und ist nicht ohne Weiteres lesbar.

Welche Daten werden gespeichert?

Standardmäßig werden Klasseninformationen und nicht statische, nicht transiente Instanzfelder gespeichert. Referenzierte Objekte werden rekursiv verarbeitet. static gehört zur Klasse, nicht zum einzelnen Objekt. transient schließt ein Feld von der Standardserialisierung aus. Methoden werden nicht gespeichert.

class Address implements Serializable {
    @Serial private static final long serialVersionUID = 1L;
    String city = "Krems";
}
class Customer implements Serializable {
    @Serial private static final long serialVersionUID = 1L;
    String name = "Anna";
    Address address = new Address();
    transient String password = "secret";
    static int counter = 5;
}

Nach dem Einlesen ist address.city weiterhin Krems, password hingegen null. Wäre Address nicht serialisierbar, würde writeObject bei einer nicht-null Referenz scheitern. Eine transiente Referenz oder null verhindert diesen Fehler. Threads und Sockets sind typische nicht serialisierbare Ressourcen. Gemeinsame Referenzen und zyklische Objektgraphen werden unterstützt.

transient und Standardwerte

Bei gewöhnlichen Serializable-Klassen werden Konstruktoren und Feldinitialisierungen der serialisierbaren Klassen beim Einlesen nicht ausgeführt. Ein transientes int-Feld erhält 0, boolean false und Referenzen null. Auch ein Feld mit Initialisierung transient int age = 25 wird standardmäßig als 0 wiederhergestellt. transient ist keine Verschlüsselung und schützt nicht vor explizitem Speichern.

Vererbung

class Base {
    int x = 10;
    Base() { System.out.println("Base"); }
}
class Student extends Base implements Serializable {
    @Serial private static final long serialVersionUID = 1L;
    String id;
    Student(String id) {
        this.id = id;
        System.out.println("Student");
    }
}
class InformatikStudent extends Student {
    @Serial private static final long serialVersionUID = 1L;
    InformatikStudent(String id) { super(id); }
}

Serializable wird vererbt. Beim Deserialisieren eines InformatikStudent wird der zugängliche parameterlose Konstruktor der ersten nicht serialisierbaren Superklasse Base ausgeführt, nicht der Konstruktor von Student oder InformatikStudent. Base.x wird nicht standardmäßig gespeichert; es wird durch Base initialisiert. Fehlt der zugängliche parameterlose Konstruktor, kann InvalidClassException auftreten. Bei new InformatikStudent laufen dagegen die normalen Konstruktoren.

Serialisierung beeinflussen

Java erkennt zwei spezielle private Methoden anhand ihrer exakten Signaturen. Sie sind keine Methoden des Marker-Interfaces und werden automatisch durch die Objektstreams aufgerufen. @Serial hilft, die Signaturen zu prüfen.

@Serial
private void writeObject(ObjectOutputStream out) throws IOException {
    out.defaultWriteObject(); // Standardfelder dieser Klasse
    out.writeInt(counter);   // zusätzlich ein statisches Feld
}
@Serial
private void readObject(ObjectInputStream in)
        throws IOException, ClassNotFoundException {
    in.defaultReadObject(); // Standardfelder wiederherstellen
    counter = in.readInt(); // statischen Wert explizit setzen
}

Die Reihenfolge muss übereinstimmen. defaultWriteObject und defaultReadObject dürfen nur im jeweiligen Serialisierungs-Callback verwendet werden. Ohne diese Aufrufe werden die Standardfelder nicht automatisch durch den eigenen Callback verarbeitet. Man kann auch transiente Felder explizit speichern oder abgeleitete Werte beim Lesen berechnen. Ein Caesar-Verfahren aus den Folien wäre nur ein Lernbeispiel, keine sichere Verschlüsselung.

serialVersionUID

Die Kennung dient zur Versionsprüfung. Ist die Kennung der gespeicherten Klasse ungleich der aktuell geladenen Klasse, entsteht normalerweise InvalidClassException. Eine gleiche Kennung garantiert aber nicht, dass jede Klassenänderung kompatibel ist. Ohne explizite Kennung berechnet die Serialisierung eine Standardkennung aus Klassendetails; IntelliJ kann eine Deklaration generieren.

@Serial
private static final long serialVersionUID = 1L;

Bei kompatiblen Änderungen, etwa einem neuen Feld, kann die Kennung gleich bleiben; ein neu hinzugefügtes Feld erhält beim Lesen alter Daten seinen Standardwert. Bei bewusst inkompatiblen Änderungen kann die Kennung erhöht werden.

Sicherheit

Nur vertrauenswürdige Daten deserialisieren. readObject-Callbacks vorhandener Klassen können beim Einlesen unerwünschte Aktionen auslösen; manipulierte Objektgraphen können Speicher oder CPU überlasten. ObjectInputFilter kann Klassen und Größen begrenzen, ersetzt aber keine Vertrauensprüfung. JSON und Protobuf sind häufig geeignete Alternativen für Datenaustausch; auch deren Eingaben müssen validiert werden.

Übungen

1. Person serialisieren

Erstelle Person mit name (String) und age (int). Markiere age als transient. Speichere ein selbst gewähltes Objekt in person.ser und lade es wieder. Prüfe beide Felder.

Implementiere Serializable. Verwende writeObject und readObject. age wird nicht standardmäßig gespeichert.

import java.io.*;

public class Main {
    static class Person implements Serializable {
        @Serial private static final long serialVersionUID = 1L;
        String name;
        transient int age;
        Person(String name, int age) {
            this.name = name;
            this.age = age;
        }
    }
    public static void main(String[] args) throws IOException, ClassNotFoundException {
        Person p = new Person("Anna", 25);
        try (ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("person.ser"))) {
            out.writeObject(p);
        }
        try (ObjectInputStream in = new ObjectInputStream(new FileInputStream("person.ser"))) {
            Person loaded = (Person) in.readObject();
            System.out.println(loaded.name); // Anna
            System.out.println(loaded.age); // 0
        }
    }
}

2. Statischen counter übertragen

Erweitere Person um einen statischen counter, der bei jeder Erzeugung mit new erhöht wird. Speichere den counter explizit und stelle ihn beim Laden wieder her. Setze ihn vor dem Einlesen auf 0, um die Wiederherstellung zu prüfen.

Eigene private writeObject/readObject-Methoden verwenden. Erst Standardfelder, dann counter. Der Person-Konstruktor wird beim Einlesen nicht aufgerufen.

import java.io.*;

public class Main {
    static class Person implements Serializable {
        @Serial private static final long serialVersionUID = 1L;
        String name;
        transient int age;
        static int counter;
        Person(String name, int age) {
            this.name = name;
            this.age = age;
            counter++;
        }
        @Serial
        private void writeObject(ObjectOutputStream out) throws IOException {
            out.defaultWriteObject();
            out.writeInt(counter);
        }
        @Serial
        private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
            in.defaultReadObject();
            counter = in.readInt();
        }
    }
    public static void main(String[] args) throws IOException, ClassNotFoundException {
        Person p = new Person("Anna", 25);
        try (ObjectOutputStream out = new ObjectOutputStream(new FileOutputStream("person.ser"))) {
            out.writeObject(p);
        }
        Person.counter = 0; // simuliert einen neuen Programmstart
        try (ObjectInputStream in = new ObjectInputStream(new FileInputStream("person.ser"))) {
            Person loaded = (Person) in.readObject();
            System.out.println(loaded.name); // Anna
            System.out.println(loaded.age); // 0
            System.out.println(Person.counter); // 1
        }
    }
}

Hinweis zur zweiten Übung: Der gespeicherte counter ist eine Momentaufnahme des Klassenzustands. Das Laden überschreibt den aktuellen statischen Wert für alle Person-Objekte. Das ist hier ausdrücklich gewünscht, wäre aber in einer echten Anwendung mit mehreren gespeicherten Objekten sorgfältig zu planen. Beide Lösungen sind eigenständige Main.java-Dateien; die zweite überschreibt person.ser mit ihrem eigenen Format.

Nebenläufigkeit – Threads

Start Grundlagen Threads erzeugen Zustände und Methoden Unterbrechung und Daemon Übungen

Einführung

Mehrere Aufgaben können innerhalb eines Java-Programms nebenläufig ausgeführt werden. Wir lernen Threads zu starten, zu beobachten, zu koordinieren und sauber zu beenden.

Grundlagen

Ein Prozess ist ein laufendes Programm mit eigenen Ressourcen. Threads sind Ausführungsstränge innerhalb eines Prozesses: Sie teilen sich den Heap, besitzen aber eigene Aufrufstapel. Multitasking bedeutet, dass das Betriebssystem mehrere Aufgaben koordiniert; Multithreading bedeutet mehrere Threads in einem Prozess.

Nebenläufigkeit bedeutet, dass Aufgaben überlappend vorankommen können, auch auf einem Kern durch Zeitscheiben. Parallelität bedeutet tatsächliche gleichzeitige Ausführung auf mehreren Kernen. Der Scheduler entscheidet, welcher Thread wann läuft. Erzeugung, Kontextwechsel und Koordination kosten Zeit; mehr Threads bedeuten nicht automatisch mehr Geschwindigkeit.

Platform Threads und Virtual Threads

Ein Platform Thread ist in Java typischerweise einem eigenen Betriebssystem-Thread zugeordnet. Das Betriebssystem entscheidet, wann dieser Thread ausgeführt wird. Jeder Thread benötigt Ressourcen, beispielsweise Speicher für seinen Aufrufstapel.

Virtual Threads sind leichtgewichtige Threads, die von der JVM verwaltet werden. Seit Java 21 stehen sie als reguläres Feature zur Verfügung; in Java 19 und 20 waren sie bereits als Preview-Feature enthalten. Viele Virtual Threads können sich eine kleinere Anzahl von Platform Threads teilen. Die JVM plant sie auf diesen Platform Threads ein, sodass sie auch auf mehreren CPU-Kernen parallel ausgeführt werden können.

Beispiel: Ein Webserver verarbeitet 10.000 Anfragen, die häufig auf eine Datenbankantwort warten. Bei vielen blockierenden I/O-Operationen kann die JVM einen wartenden Virtual Thread von seinem Platform Thread lösen. Dieser kann inzwischen eine andere Aufgabe ausführen. Sobald die Antwort verfügbar ist, kann der Virtual Thread seine Arbeit fortsetzen.

Platform Thread Virtual Thread
Typischerweise eigener Betriebssystem-Thread Teilt sich Platform Threads mit anderen Virtual Threads
Höherer Ressourcenbedarf pro Thread Geringerer Ressourcenbedarf pro Thread
Vom Betriebssystem eingeplant Von der JVM auf Platform Threads eingeplant

Wichtig: Virtual Threads machen CPU-intensive Berechnungen nicht automatisch schneller. Ihr Vorteil liegt vor allem bei vielen Aufgaben, die häufig auf I/O warten.

Virtual Thread starten

Thread t = Thread.startVirtualThread(() -> {
    System.out.println("Hello World");
});

t.join(); // wartet auf das Ende des Virtual Threads

startVirtualThread() erzeugt und startet den Thread sofort. Ein zusätzlicher Aufruf von start() ist nicht notwendig. join() wartet auf seine Beendigung.

Threads erzeugen

Es gibt zwei klassische Möglichkeiten, einen Platform Thread zu erstellen. Beide starten den Thread mit start().

Variante 1: Von Thread erben

class MyThread extends Thread {

    @Override
    public void run() {
        System.out.println("Thread arbeitet");
    }
}

public class Main {

    public static void main(String[] args) {
        MyThread t = new MyThread();
        t.start();
    }
}

MyThread erbt von Thread und überschreibt run(). Das Objekt t ist selbst ein Thread. start() startet den neuen Thread, der die überschriebene run()-Methode ausführt.

Ausgabe: Thread arbeitet

Variante 2: Runnable implementieren

class MyTask implements Runnable {

    @Override
    public void run() {
        System.out.println("Thread arbeitet");
    }
}

public class Main {

    public static void main(String[] args) {
        MyTask task = new MyTask();

        Thread t = new Thread(task);
        t.start();
    }
}

MyTask implementiert Runnable und beschreibt die Aufgabe. Ein Runnable ist selbst kein Thread. Deshalb wird task dem Konstruktor von Thread übergeben. start() startet den neuen Thread, der task.run() ausführt.

Ausgabe: Thread arbeitet

Kurzform: Runnable mit Lambda

public class Main {

    public static void main(String[] args) {
        Runnable task = () -> {
            System.out.println("Thread arbeitet");
        };

        Thread t = new Thread(task);
        t.start();
    }
}

Runnable ist ein funktionales Interface mit der abstrakten Methode void run(). Deshalb kann die Aufgabe auch durch einen Lambda-Ausdruck beschrieben werden. Das ist eine Kurzform der zweiten Variante, keine neue Art der Thread-Erzeugung.

Ausgabe: Thread arbeitet

Vergleich: Runnable trennt die Aufgabe von ihrer Ausführung. Die Aufgabenklasse kann außerdem von einer anderen Klasse erben. Bei extends Thread ist die Vererbung bereits festgelegt. Daher wird Runnable häufig bevorzugt.

start() versus run()

Thread t = new Thread(() ->
    System.out.println(Thread.currentThread().getName()), "Worker");
t.run();   // main: normaler Methodenaufruf
t.start(); // Worker: neuer Ausführungsstrang
t.join();  // main wartet auf Worker
// t.start(); // IllegalThreadStateException

start() startet einen neuen Thread, der die run()-Methode ausführt. Der aufrufende Thread (z. B. der Main-Thread) setzt seine Ausführung fort, ohne auf das Ende des neuen Threads zu warten.

run() führt bei einem direkten Aufruf die Methode im aktuellen Thread aus. Erst wenn die Methode beendet ist, wird der nächste Befehl ausgeführt. Es entsteht kein neuer Thread.

Ein Thread kann nur einmal mit start() gestartet werden. join() kann InterruptedException werfen; die main-Methode kann throws InterruptedException deklarieren.

Ausgabereihenfolge

System.out.println("Begin");
Thread a = new Thread(() -> System.out.println("A"));
Thread b = new Thread(() -> System.out.println("B"));
a.start();
b.start();
System.out.println("End");
a.join();
b.join();
System.out.println("Fertig");

Begin steht zuerst, Fertig zuletzt. A, B und End können in unterschiedlicher Reihenfolge erscheinen. start() garantiert nicht, dass A vor B ausgeführt wird.

Zustände und Methoden

Thread.State Bedeutung
NEW Erzeugt, noch nicht gestartet
RUNNABLE Ausführbar oder gerade laufend; kein separater Java-Zustand RUNNING
BLOCKED Wartet auf einen intrinsischen Monitor (synchronized)
WAITING Wartet ohne Zeitlimit, z. B. join(), wait(), park()
TIMED_WAITING Wartet mit Zeitlimit, z. B. sleep(), join(1000)
TERMINATED run() beendet, normal oder durch unbehandelte Ausnahme

getState() liefert nur eine Momentaufnahme. isAlive() ist nach start() bis zur Beendigung true. ReentrantLock-Warten ist nicht zwingend BLOCKED; typischerweise WAITING/TIMED_WAITING.

Methode Erklärung
currentThread() Statisch: Referenz auf den gerade ausführenden Thread
getName()/setName(String) Name lesen/setzen; dient der Diagnose, nicht der Identität
threadId() Eindeutige ID während der Lebensdauer; Java 21 bevorzugt gegenüber deprecated getId()

isDaemon()/setDaemon(boolean) Daemon-Status abfragen/setzen; bei Platform Threads vor start() setzen

join mit Timeout

Thread t = new Thread(() -> {
    try {
        Thread.sleep(500);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
});
t.start();
t.join(100);
System.out.println(t.isAlive()); // meist true, nicht garantiert
t.join();
System.out.println(t.isAlive()); // false

join(100) wirft nicht wegen Zeitablaufs. InterruptedException entsteht, wenn der wartende Thread unterbrochen wird. Nach erfolgreichem join() sind die Aktionen des beendeten Threads für den Aufrufer sichtbar (happens-before).

Unterbrechung und Daemon

interrupt() ist eine kooperative Aufforderung, keine Zwangsbeendigung. Bei sleep, wait und join wird gewöhnlich InterruptedException ausgelöst und das Interrupt-Flag gelöscht. Bei normaler Berechnung wird das Flag gesetzt; der Code muss reagieren. Warten auf synchronized ist nicht interruptibel. 

Thread worker = new Thread(() -> {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            System.out.println("Arbeite");
            Thread.sleep(100);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // Flag wieder setzen
    }
});
worker.start();
Thread.sleep(250);
worker.interrupt();
worker.join();
System.out.println("Beendet");

isInterrupted() prüft das Flag des betreffenden Threads ohne es zu löschen. Thread.interrupted() prüft das Flag des aktuellen Threads und löscht es. Ein catch sollte die Unterbrechung nicht unbemerkt verschlucken; weiterwerfen, beenden oder Flag wieder setzen.

Daemon Threads verhindern das JVM-Ende nicht. Sie haben nicht automatisch niedrige Priorität. Platform Threads erben normalerweise den Daemon-Status ihres Erzeugers; Virtual Threads sind immer Daemons. Die JVM wartet nicht darauf, dass Daemons ihre Arbeit oder finally-Blöcke beenden. 

Thread t = new Thread(() -> System.out.println("Hintergrund"));
t.setDaemon(true);
t.start();
// Ohne join ist die Ausgabe nicht garantiert.
t.join(); // jetzt wird auf die Beendigung gewartet

Übungen

1. Zwei Teilberechnungen

Berechne die Summen 1 bis 100 und 101 bis 200 in zwei Threads. Gib erst danach die Gesamtsumme aus.

Jeder Thread schreibt in ein eigenes Arrayelement. Warte mit join auf beide.

public class Main {
    public static void main(String[] args) throws InterruptedException {
        int[] sums = new int[2];

        Thread a = new Thread(() -> {
            for (int i = 1; i <= 100; i++) {
                sums[0] += i;
            }
        });

        Thread b = new Thread(() -> {
            for (int i = 101; i <= 200; i++) {
                sums[1] += i;
            }
        });

        // Beide Threads starten
        a.start();
        b.start();

        // Auf beide Threads warten
        a.join();
        b.join();

        System.out.println(sums[0] + sums[1]); // 20100
    }
}

Warum funktioniert das ohne synchronized?

1. Unterschiedliche Speicherstellen: Thread a verändert ausschließlich sums[0], Thread b ausschließlich sums[1]. Obwohl beide dasselbe Array verwenden, schreiben sie nicht auf dasselbe Array-Element. Daher können sie die Änderungen des jeweils anderen Threads nicht überschreiben (keine Lost Updates).

2. Warten auf die Berechnungen: a.join() und b.join() sorgen dafür, dass der Main-Thread erst nach Beendigung beider Threads die Gesamtsumme berechnet. Beide Threads wurden vorher gestartet und können nebenläufig arbeiten.

3. Sichtbarkeit: Nach erfolgreichem join() sind die Änderungen des beendeten Threads für den Main-Thread sichtbar (Happens-before-Beziehung). Damit liest main die vollständig berechneten Werte.

Thread Berechnung Ergebnis
a 1 + ... + 100 5050
b 101 + ... + 200 15050
main 5050 + 15050 20100

Was passiert ohne join()?

a.start();
b.start();

System.out.println(sums[0] + sums[1]); // Ergebnis nicht garantiert

Der Main-Thread könnte die Summe ausgeben, bevor die beiden Threads fertig sind. Würden beide Threads hingegen dasselbe Array-Element mit += verändern, könnten Lost Updates auftreten, selbst mit join().

Merke: Nicht jeder Zugriff mehrerer Threads auf dasselbe Objekt erfordert synchronized. Hier sind die getrennten Speicherstellen und join() ausreichend.

2. Lager ohne Synchronisation

Ein Produzent liefert, ein Konsument verkauft. Beide verwenden dieselbe Lagerinstanz mit Bestand 100 und maximal 15 Transaktionen. Beobachte mehrmals die Ausgaben und erkläre mögliche Fehler.

bestand += anzahl und transaktionen++ bestehen aus mehreren Schritten. istOffen und die nachfolgende Aktion sind nicht gemeinsam atomar. 

public class Main {
    static class Lager {
        int bestand = 100;
        int transaktionen = 0;

        boolean istOffen() {
            return transaktionen < 15;
        }

        void liefere(int anzahl) {
            bestand += anzahl;
            transaktionen++;
            System.out.println("Lieferung: " + bestand);
        }

        void verkaufe(int anzahl) {
            bestand -= anzahl;
            transaktionen++;
            System.out.println("Verkauf: " + bestand);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Lager lager = new Lager();

        Thread produzent = new Thread(() -> {
            for (int i = 0; i < 15 && lager.istOffen(); i++) {
                lager.liefere(10);
            }
        });

        Thread konsument = new Thread(() -> {
            for (int i = 0; i < 15 && lager.istOffen(); i++) {
                lager.verkaufe(10);
            }
        });

        produzent.start();
        konsument.start();

        produzent.join();
        konsument.join();

        System.out.println("Bestand: " + lager.bestand);
        System.out.println("Transaktionen: " + lager.transaktionen);
    }
}

Warum ist dieses Programm fehlerhaft?

Produzent und Konsument greifen auf dieselben Attribute bestand und transaktionen zu. Die Zugriffe sind nicht synchronisiert. Folgende Fehler können auftreten:

1. Lost Updates (verlorene Änderungen)

bestand += 10 und bestand -= 10 bestehen jeweils aus Lesen, Berechnen und Speichern. Diese Schritte können sich überschneiden. Beispiel bei einem Anfangsbestand von 100:

Schritt Produzent Konsument
1 Liest 100
2 Liest 100
3 Berechnet 110
4 Berechnet 90
5 Speichert 110
6 Speichert 90

Der Endbestand beträgt 90 statt 100. Die Lieferung wurde überschrieben. Dasselbe Problem kann bei transaktionen++ auftreten: Zwei Transaktionen werden durchgeführt, aber der Zähler steigt nur um eins.

2. Negative Bestände

Die Methode verkaufe() prüft nicht, ob genügend Ware vorhanden ist. Wenn der Konsument beispielsweise elfmal verkauft, bevor der Produzent liefert, sinkt der Bestand von 100 auf -10. Dieser Fehler kann auch ohne Nebenläufigkeit auftreten. Eine korrekte Lösung muss den Bestand vor dem Verkauf prüfen und Prüfung und Änderung gemeinsam schützen.

3. Inkonsistente Ausgaben

Der Produzent erhöht den Bestand von 100 auf 110. Bevor er die Ausgabe ausführt, verkauft der Konsument 10 Stück. Der Produzent kann nun „Lieferung: 100“ ausgeben, obwohl seine Lieferung den Bestand auf 110 erhöht hatte. Die Ausgabe passt dann nicht mehr zum eigenen Vorgang.

4. Mehr als 15 Transaktionen

Bei 14 Transaktionen können beide Threads istOffen() aufrufen und true erhalten. Anschließend führen beide ihre Aktion durch. Damit finden 16 Transaktionen statt, obwohl nur 15 erlaubt sind. Der gespeicherte Zähler kann wegen Lost Updates sogar weniger anzeigen.

Die Prüfung istOffen() und die anschließende Transaktion müssen gemeinsam geschützt werden. Einzelne synchronisierte Methoden reichen dafür nicht aus, wenn die Prüfung weiterhin getrennt von der Aktion erfolgt.

5. Warum sind die Schleifen begrenzt?

Die Bedingung i < 15 begrenzt jeden Thread auf höchstens 15 Durchläufe, also insgesamt höchstens 30 Aktionen. Ohne diese zusätzliche Grenze wäre bei fehlender Synchronisation nicht garantiert, dass ein Thread die Änderungen am Transaktionszähler rechtzeitig erkennt. Die Grenze verhindert hier eine unbegrenzte Schleife, behebt aber keinen der genannten Fehler.

Fazit: join() wartet auf beide Threads und macht ihre Ergebnisse sichtbar. Es verhindert aber keine konkurrierenden Zugriffe während der Ausführung. Eine korrekte Lagerlösung muss Bestandsprüfung, Transaktionslimit und Änderungen gemeinsam synchronisieren.

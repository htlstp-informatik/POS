Einführung

Aufbauend auf Threads koordinieren wir gemeinsame Daten und Wartebedingungen. Beispiele verwenden Java 21; Codeausschnitte benötigen die passenden Imports (java.util.concurrent.*, java.util.concurrent.locks.*, java.util.concurrent.atomic.*) und gegebenenfalls throws InterruptedException in main.

Race Conditions und Fehlerquellen

Gemeinsame veränderbare Daten benötigen eine konsistente Synchronisationsstrategie. Ein Lost Update entsteht beispielsweise bei bestand += 10: Lesen, Berechnen, Schreiben sind zusammen nicht atomar.

Schritt Lieferant Kunde
1 liest 100 liest 100
2 berechnet 110 berechnet 90
3 schreibt 110 schreibt 90

Ergebnis 90 statt 100. Auch ein einzelner Schreiber und mehrere Leser können ohne Sichtbarkeitsgarantie inkonsistente Daten beobachten. Das Beispiel ist eine mögliche logische Reihenfolge, keine garantierte Beschreibung von CPU-Registern.

Problem Bedeutung
Race Condition Ergebnis hängt von der zeitlichen Reihenfolge ab
Data Race Konfligierende Speicherzugriffe ohne happens-before, mindestens einer schreibt
Deadlock Threads warten zyklisch aufeinander
Livelock Threads reagieren aktiv aufeinander, ohne Fortschritt
Starvation Thread erhält dauerhaft nicht benötigte Ressourcen oder Ausführungsgelegenheiten
Spurious Wakeup Warten endet ohne passendes Signal; Bedingung erneut prüfen

Deadlock vermeiden

Wenn A zuerst Lock 1 und B zuerst Lock 2 hält und beide den jeweils anderen benötigen, kann ein Deadlock entstehen. Einheitliche Lock-Reihenfolge verhindert diesen Zyklus. Private Locks helfen bei der Kapselung, verhindern aber nicht automatisch Deadlocks.

Monitor und synchronized

Jedes Java-Objekt besitzt einen intrinsischen Monitor. synchronized erwirbt diesen Monitor vor dem geschützten Bereich und gibt ihn beim Verlassen automatisch frei, auch bei Exceptions. Nur ein Thread kann ihn gleichzeitig halten; derselbe Thread darf ihn mehrfach erwerben (reentrant). Nicht synchronisierte Methoden werden dadurch nicht automatisch gesperrt. 

class Counter {
    private int count;
    public synchronized void increment() {
        count++;
    }
    public synchronized int get() {
        return count;
    }
}

Beide Methoden sperren this. Zwei verschiedene Counter-Objekte haben unterschiedliche Monitore. Gibt ein Thread den Monitor frei, sind seine vorherigen Änderungen für einen anderen Thread sichtbar, der anschließend denselben Monitor erwirbt. Beispiel: Thread A erhöht count auf 1 und verlässt increment(). Ruft Thread B danach get() auf, liest er 1 (sofern kein weiterer Thread den Wert geändert hat). synchronized legt jedoch nicht fest, welcher Thread zuerst den Monitor erwirbt. 

class Counter {
    private int count;
    private final Object lock = new Object();
    public void increment() { synchronized (lock) {
        count++;
    } }
    public int get() { synchronized (lock) {
        return count;
    } }
}

private verhindert fremde Zugriffe auf das Lock-Objekt, final verhindert den Austausch der Referenz. Alle Zugriffe auf count müssen dieselbe Strategie verwenden. Eine static synchronized Methode sperrt Counter.class, nicht this. Ein Konstruktor darf nicht synchronized deklariert werden; ein Block darin ist möglich. this.getClass() kann bei Unterklassen ein anderes Class-Objekt liefern als Counter.class. 

class GlobalCounter {
    private static int count;
    public static synchronized void increment() {
        count++;
    }
    public static synchronized int get() {
        return count;
    }
}

Ein synchronisierter Getter und ein synchronisierter Setter machen eine Folge wie if (get() < 15) increment() nicht atomar. Prüfung und Änderung müssen gemeinsam geschützt werden. sleep() gibt den Monitor nicht frei.

wait, notify und notifyAll

Busy Waiting prüft ständig eine Bedingung und verbraucht CPU-Zeit. Innerhalb von synchronized kann es sogar den Lieferanten aussperren. Auch sleep() löst dieses Problem nicht, weil der Monitor gehalten bleibt.

Methode Verhalten
wait() Gibt den Monitor des aufgerufenen Objekts frei und wartet; erwirbt ihn vor Rückkehr erneut
wait(long millis) Wie wait(), zusätzlich Zeitlimit; 0 bedeutet unbegrenzt
notify() Wählt einen Thread aus dem Wait-Set dieses Objekts
notifyAll() Weckt alle Threads aus diesem Wait-Set

Alle drei Methoden verlangen, dass der aktuelle Thread genau den Monitor des betreffenden Objekts hält, sonst IllegalMonitorStateException. wait gibt keine anderen gehaltenen Monitore frei. notify gibt den Monitor nicht sofort frei. Geweckte Threads konkurrieren nach Freigabe erneut um ihn. Signale werden nicht gespeichert. while ist nötig wegen Spurious Wakeups und weil ein anderer Thread die Bedingung vorher wieder ändern kann. 

class Lager {
    private int bestand;
    private final int capacity = 100;
    public synchronized void liefere(int n) throws InterruptedException {
        if (n <= 0 || n > capacity) throw new IllegalArgumentException();
        while (bestand > capacity - n) wait();
        bestand += n;
        notifyAll();
    }
    public synchronized void verkaufe(int n) throws InterruptedException {
        if (n <= 0 || n > capacity) throw new IllegalArgumentException();
        while (bestand < n) wait();
        bestand -= n;
        notifyAll();
    }
}

Ein Kunde mit Bedarf 10 wartet bei Bestand 0. Der Lieferant erwirbt den freigegebenen Monitor, liefert 10 und signalisiert. Erst nach Verlassen der Methode kann der Kunde den Monitor wieder erwerben und die Bedingung prüfen. Bei unterschiedlichen Mengen ist notifyAll sinnvoll. Für endliche Programme braucht man zusätzlich ein Abschlussprotokoll, damit niemand nach Ende der Produktion ewig wartet.

ReentrantLock und Condition

Ein expliziter Lock erlaubt flexible Erwerbsarten. Anders als synchronized muss er vom Besitzer explizit freigegeben werden. lock() wartet auch bei Interrupt weiter; lockInterruptibly() erlaubt Abbruch. tryLock() liefert sofort boolean, tryLock(time, unit) wartet begrenzt und ist interruptibel. 

Lock lock = new ReentrantLock();
if (lock.tryLock()) {
    try {
        // kritischer Bereich
    } finally {
        lock.unlock();
    }
}

Bei false wurde kein Lock erworben. Ein unlock wäre falsch. Bei lockInterruptibly() steht der Erwerb ebenfalls vor dem try/finally. Condition erlaubt mehrere Wait-Sets pro Lock; await() gibt den zugehörigen Lock frei, signal()/signalAll() benötigen ihn. Auch hier immer while. 

class Lager {
    private final Lock lock = new ReentrantLock();
    private final Condition ware = lock.newCondition();
    private final Condition platz = lock.newCondition();
    private int bestand;
    public void liefere(int n) throws InterruptedException {
        if (n <= 0 || n > 100) throw new IllegalArgumentException();
        lock.lockInterruptibly();
        try {
            while (bestand > 100 - n) platz.await();
            bestand += n;
            ware.signalAll();
        } finally {
        lock.unlock();
    }
    }
    public void verkaufe(int n) throws InterruptedException {
        if (n <= 0 || n > 100) throw new IllegalArgumentException();
        lock.lockInterruptibly();
        try {
            while (bestand < n) ware.await();
            bestand -= n;
            platz.signalAll();
        } finally {
        lock.unlock();
    }
    }
}

signal() weckt nur einen Wartenden der jeweiligen Condition, nicht alle. Bei verschiedenen Mengen kann der ausgewählte Thread weiterhin nicht fortfahren; signalAll() ist hier robuster. Ein ReentrantLock ist nicht der intrinsische Monitor des Lock-Objekts: lock.lock() berechtigt nicht zu lock.wait().

Producer/Consumer

BlockingQueue koordiniert Produzenten und Konsumenten automatisch. ArrayBlockingQueue hat feste Kapazität und FIFO; LinkedBlockingQueue hat optional eine feste Kapazitätsgrenze, die nicht nachträglich geändert wird. PriorityBlockingQueue ist nicht FIFO. null ist nicht erlaubt.

Einfügen Entnehmen Verhalten
add(e) remove() Exception bei voll/leer
offer(e) poll() false/null bei voll/leer
put(e) take() Wartet interruptibel
offer(e,t,u) poll(t,u) Wartet begrenzt; false/null bei Timeout 
BlockingQueue<Integer> q = new ArrayBlockingQueue<>(5);
Runnable producer = () -> {
    try {
        for (int i=0; i<10; i++) q.put(i);
        q.put(-1); // Ende-Signal, kein Nutzwert
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
};
Thread a = new Thread(producer), b = new Thread(producer);
a.start(); b.start();
int ends = 0;
while (ends < 2) {
    int value = q.take();
    if (value == -1) ends++;
    else System.out.println(value);
}
a.join(); b.join(); // 20 Nutzwerte, Reihenfolge variabel

Das Beispiel setzt normalen Abschluss beider Produzenten voraus; bei Abbruch braucht es ein gemeinsames Abbruchprotokoll. PipedInputStream/PipedOutputStream verbinden zwei Threads über einen internen Bytepuffer. Lesen blockiert bei leerem Puffer, Schreiben bei vollem. Der Schreiber schließt den Stream, damit der Leser EOF erkennt. Für Text gibt es PipedReader/PipedWriter; für Objekte ist BlockingQueue meist einfacher.

Semaphore, Latch und Barrier

Semaphore

Eine Semaphore verwaltet Permits. acquire() nimmt eines und wartet interruptibel, wenn keines verfügbar ist. release() erhöht den Zähler, auch ohne vorheriges acquire; Permits haben keinen Besitzer. Deshalb nur nach erfolgreichem Erwerb freigeben, wenn eine Ressource begrenzt wird. Fairness true bevorzugt wartende Threads in FIFO-Reihenfolge an internen Erwerbspunkten; untimed tryAcquire darf vorbeiziehen. 

Semaphore sem = new Semaphore(2, true);
Runnable print = () -> {
    try {
        sem.acquire();
        try {
        System.out.println("Drucke");
        Thread.sleep(100);
    }
        finally {
        sem.release();
    }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
};
// Maximal zwei Threads gleichzeitig im Druckbereich.

acquire(n) erwirbt n Permits; tryAcquire() liefert sofort boolean; tryAcquire(timeout, unit) wartet begrenzt; acquireUninterruptibly wartet trotz Interrupt und erhält den Interruptstatus. availablePermits() ist eine Momentaufnahme; drainPermits() setzt den verfügbaren Zähler auf 0 und liefert den vorherigen Wert (auch negativ möglich). getQueueLength() ist eine Schätzung, hasQueuedThreads() eine Momentaufnahme. Negative Startwerte sind erlaubt; release kann den Startwert überschreiten.

CountDownLatch

Ein einmaliger Countdown. countDown() reduziert den Zähler bis 0, await() wartet interruptibel auf 0; danach bleibt das Latch offen. await(timeout, unit) liefert true bei 0, false bei Timeout. getCount() liefert den aktuellen Stand. Ein Latch zählt Ereignisse, nicht automatisch beendete Threads. 

CountDownLatch done = new CountDownLatch(3);
for (int i=0;i<3;i++) new Thread(() -> {
    try {
        System.out.println("Teilaufgabe");
    }
    finally {
        done.countDown();
    }
}).start();
done.await();
System.out.println("Alle Teilaufgaben abgeschlossen");

CyclicBarrier

Eine feste Anzahl Teilnehmer wartet an einem Treffpunkt. await() liefert einen Ankunftsindex: letzter Teilnehmer 0, erster parties-1. Eine optionale Barrier-Aktion läuft im letzten ankommenden Thread vor Freigabe. Nach erfolgreicher Runde ist die Barriere wiederverwendbar. Timeout oder Interrupt eines Wartenden bricht die Runde; andere erhalten BrokenBarrierException. reset() bricht aktuelle Wartende ab und startet eine neue Generation. 

CyclicBarrier barrier = new CyclicBarrier(3,
    () -> System.out.println("Alle bereit"));
Runnable worker = () -> {
    try {
        for (int r=0;r<2;r++) {
            System.out.println("Vorbereitung " + r);
            barrier.await();
            System.out.println("Weiter " + r);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
      catch (BrokenBarrierException e) {
        System.out.println("Abbruch");
    }
};
for (int i=0;i<3;i++) new Thread(worker).start();

getParties(), getNumberWaiting(), isBroken() liefern Teilnehmerzahl, momentane Wartezahl und Fehlerzustand. Latch ist ein einmaliges Signal, Barrier ein wiederholbarer Treffpunkt; beide sind keine Lager-Warteschlange.

ExecutorService, Callable und Future

ExecutorService trennt Aufgaben von Thread-Verwaltung. FixedThreadPool(n) begrenzt aktive Worker, nutzt aber eine unbeschränkte Warteschlange. CachedThreadPool kann viele Threads erzeugen; SingleThreadExecutor führt Aufgaben seriell aus; ScheduledThreadPool plant verzögerte und wiederkehrende Aufgaben. Java 21 bietet newVirtualThreadPerTaskExecutor() für viele blockierende Aufgaben. 

try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
    Callable<Integer> task = () -> 21 * 2;
    Future<Integer> result = pool.submit(task);
    System.out.println(result.get()); // 42
}

Callable.call() liefert einen Wert und darf checked Exceptions werfen. Runnable.run() liefert void. submit liefert Future; execute liefert keinen Rückgabewert. Future.get wartet auf Abschluss; ExecutionException kapselt Fehler der Aufgabe, CancellationException signalisiert Abbruch, InterruptedException betrifft den wartenden Thread. get(timeout, unit) wirft TimeoutException, bricht die Aufgabe aber nicht ab. cancel(true) versucht zu unterbrechen; isDone umfasst Erfolg, Fehler und Abbruch, isCancelled nur Abbruch.

Methode Bedeutung
invokeAll(tasks) Wartet auf alle, liefert Futures in Eingabereihenfolge
invokeAny(tasks) Liefert Ergebnis einer erfolgreich abgeschlossenen Aufgabe; nicht zwingend der zuerst beendeten
shutdown() Keine neuen Aufgaben, bereits eingereichte werden abgearbeitet
shutdownNow() Versucht laufende Aufgaben zu unterbrechen, liefert noch nicht gestartete Aufgaben
awaitTermination(t,u) Wartet nach Shutdown; true bei Terminierung, false bei Timeout 
pool.shutdown();
try {
    if (!pool.awaitTermination(1, TimeUnit.SECONDS)) pool.shutdownNow();
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}

Java 21: ExecutorService.close() wartet auf Beendigung und kann bei Interrupt shutdownNow auslösen. FutureTask implementiert Runnable und Future; new Thread(new FutureTask<>(callable)) ist möglich, new Thread(future) mit statischem Typ Future dagegen nicht. ForkJoinPool ist selbst ein ExecutorService und eignet sich für rekursive Teilaufgaben mit Work-Stealing.

volatile und AtomicInteger

volatile garantiert Sichtbarkeit und Ordnungsregeln des Java Memory Model: Ein volatile-Schreibzugriff happens-before einem späteren Lesezugriff derselben Variablen. Es bedeutet nicht zwingend direkten Hauptspeicherzugriff. volatile int x macht x++ nicht atomar. Eine volatile Referenz macht nicht alle Felder des referenzierten Objekts threadsicher. 

class Worker implements Runnable {
    private volatile boolean running = true;
    public void stop() {
        running = false;
    }
    public void run() {
        while (running) {
        /* kurze Arbeit */
    }
    }
}

Für einen einfachen Zähler eignen sich atomare Operationen. getAndIncrement liefert den alten Wert, incrementAndGet den neuen; analog decrementAndGet, getAndDecrement, addAndGet und getAndAdd. compareAndSet(expected, update) ändert nur bei passendem aktuellem Wert und liefert boolean. 

AtomicInteger count = new AtomicInteger();
Runnable task = () -> {
    for (int i=0;i<1000;i++) count.incrementAndGet();
};
Thread a = new Thread(task), b = new Thread(task);
a.start(); b.start(); a.join(); b.join();
System.out.println(count.get()); // garantiert 2000

Ohne join könnte die Ausgabe vor Abschluss erfolgen. Atomare Einzeloperationen machen mehrere zusammengehörige Felder nicht automatisch konsistent.

Übungen und Monitor-Aufgaben

1. Monitor-Varianten I–IV (Original)

Analysiere den Originalcode: Welche Threads sperren denselben Monitor? Welche Reihenfolgen und Laufzeiten sind möglich? 

package monitor;

public class Monitor implements Runnable {
    private int variant = 0;
    private int counter_instanz = 0;
    private static int counter_class = 0;
    private final Object lock = new Object();

    public Monitor(int variant) {
        this.variant = variant;
    }

    public static void increment_1() {
        synchronized (Monitor.class) {
            System.out.println("Start: " + Thread.currentThread().getName());
            counter_class++;
            try {
                Thread.sleep(5000);
            } catch (InterruptedException ie) {}
        }
    }

    public synchronized void increment_2() {
        synchronized (this.getClass()) {
            System.out.println("Start: " + Thread.currentThread().getName());
            this.counter_instanz++;
            try {
                Thread.sleep(5000);
            } catch (InterruptedException ie) {}
        }
    }

    public synchronized void increment_3() {
        System.out.println("Start: " + Thread.currentThread().getName());
        this.counter_instanz++;
        try {
            Thread.sleep(3000);
        } catch (InterruptedException ie) {}
    }

    public void increment_4() {
        synchronized (lock) {
            System.out.println("Start: " + Thread.currentThread().getName());
            counter_instanz++;
            try {
                Thread.sleep(3000);
            } catch (InterruptedException ie) {}
        }
    }

        // Variante I - IV
    public static void start(int variant) {
        Monitor m1 = new Monitor(variant);
        Thread thread1 = new Thread(m1);
        thread1.start();

        Monitor m2 = new Monitor(variant);
        Thread thread2 = new Thread(m2);
        thread2.start();

        Monitor m3 = new Monitor(variant);
        Thread thread3 = new Thread(m3);
        thread3.start();

        Thread thread4 = new Thread(m3);
        thread4.start();
    }

    @Override
    public void run() {
        switch  (variant){
            case 1 -> {
                increment_1();
            }
            case 2 -> {
                increment_2();
            }
            case 3 -> {
                increment_3();
            }
            case 4 -> {
                increment_4();
            }
            default -> {}
        }
        System.out.println("Fertig: " + Thread.currentThread().getName());

    public static void main(String[] args) { // Output?
         start(1);        
         start(2);        
         start(3);

m3 wird zweimal verwendet. main wartet nicht zwischen den Varianten. sleep gibt keinen Monitor frei.

Variante Monitor Ergebnis bei isoliertem Start
1 Monitor.class Alle vier nacheinander; counter_class +4; ca. 20 s
2 this und this.getClass() Alle vier nacheinander über Monitor.class; ca. 20 s
3 this m1, m2 und m3 parallel möglich; zwei m3-Aufrufe nacheinander; ca. 6 s
4 privates lock je Instanz Wie 3; anderer Monitor als this; ca. 6 s

Die Zeiten sind idealisierte Untergrenzen bei ununterbrochenem sleep und ohne Scheduling-Verzögerung. Im Original startet main alle vier Gruppen ohne join: 16 Threads überlappen. Varianten 1 und 2 teilen Monitor.class (hier keine Unterklassen); insgesamt etwa 40 Sekunden allein für diese acht geschützten Schlafphasen. Varianten 3 und 4 verwenden jeweils neue Instanzen und können gleichzeitig laufen. Start-Ausgaben innerhalb desselben Monitors sind serialisiert; Fertig steht außerhalb des Locks und kann nach dem nächsten Start erscheinen. Keine feste Gesamtausgabe. Die Instanzzähler sind je Gruppe 1, 1, 2 (Varianten 2–4); Variante 1 erhöht nur den statischen Zähler. Leere catch-Blöcke sind absichtlich im Original erhalten, in produktivem Code Interrupt behandeln.

    Lock lock2 = new ReentrantLock();

Vergleiche jeweils den gehaltenen Monitor bzw. Lock mit dem Objekt, auf dem gewartet oder signalisiert wird.

Fall Fehler Korrektur
I lock.wait() ohne Besitz von lock synchronized(lock) und while(Bedingung)
II wait() auf this ohne Monitor synchronized(this) oder synchronized Methode
III Methode hält this, wartet aber auf Thread.currentThread() wait() auf this verwenden
IV ArrayList nicht threadsicher, auch getSize ungeschützt beide Methoden synchronized oder gemeinsamer privater Lock
V ReentrantLock erworben, aber Object.wait() auf this Condition erzeugen und await() unter lock verwenden
VI signal() ohne zugehörigen Lock lock.lock(); try { full.signal(); } finally { lock.unlock(); }
VII lock1 gehalten, empty gehört zu lock2 lock2 erwerben und im finally freigeben

I, II, III, V, VI, VII führen bei den gezeigten gewöhnlichen Aufrufen zu IllegalMonitorStateException; IV kann falsche Ergebnisse oder beschädigte Listenstruktur verursachen. Ein korrektes wait/await braucht eine veränderbare Bedingung und einen Signalisierer; while(true) allein würde nie regulär enden.

3. Zusatz: Lager mit maximal 15 Transaktionen

Erweitere das Lager aus der Threads-Seite: Startbestand 100, maximal 200 Stück und höchstens 15 erfolgreiche Transaktionen. Lieferant und Kunde arbeiten mit jeweils 10 Stück. Verwende die getrennten Methoden liefere() und verkaufe(). Warte bei vollem oder leerem Lager und beende beide Threads nach der 15. Transaktion.

Synchronisiere beide Methoden auf demselben Lagerobjekt. Prüfe Bestand und Transaktionsgrenze innerhalb des Monitors. Verwende while mit wait() und wecke nach jeder erfolgreichen Transaktion alle Wartenden mit notifyAll(). 

public class Main {
    static class Lager {
        private int bestand = 100;
        private int transaktionen = 0;
        private static final int MAX_BESTAND = 200;
        private static final int MAX_TRANSAKTIONEN = 15;

        public synchronized boolean istOffen() {
            return transaktionen < MAX_TRANSAKTIONEN;
        }

        public synchronized boolean liefere(int anzahl) throws InterruptedException {
            if (anzahl <= 0 || anzahl > MAX_BESTAND) {
                throw new IllegalArgumentException();
            }

            while (istOffen() && bestand > MAX_BESTAND - anzahl) {
                wait();
            }

            if (!istOffen()) {
                return false;
            }

            bestand += anzahl;
            transaktionen++;
            System.out.println("Lieferung: " + bestand + " / " + transaktionen);
            notifyAll();
            return true;
        }

        public synchronized boolean verkaufe(int anzahl) throws InterruptedException {
            if (anzahl <= 0 || anzahl > MAX_BESTAND) {
                throw new IllegalArgumentException();
            }

            while (istOffen() && bestand < anzahl) {
                wait();
            }

            if (!istOffen()) {
                return false;
            }

            bestand -= anzahl;
            transaktionen++;
            System.out.println("Verkauf: " + bestand + " / " + transaktionen);
            notifyAll();
            return true;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Lager lager = new Lager();

        Thread produzent = new Thread(() -> {
            try {
                while (lager.liefere(10)) {
                    // Weiter liefern, solange das Lager offen ist.
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread konsument = new Thread(() -> {
            try {
                while (lager.verkaufe(10)) {
                    // Weiter verkaufen, solange das Lager offen ist.
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        produzent.start();
        konsument.start();

        produzent.join();
        konsument.join();

        System.out.println("Bestand: " + lager.bestand);
        System.out.println("Transaktionen: " + lager.transaktionen); // 15
    }
}

Warum funktioniert diese Lösung?

Beide Threads verwenden dasselbe Lagerobjekt. Die synchronisierten Instanzmethoden erwerben dessen Monitor (this). Solange ein Thread eine Transaktion ausführt, kann der andere keine der synchronisierten Methoden auf diesem Objekt ausführen. Die Prüfung, Bestandsänderung und Erhöhung des Transaktionszählers sind damit gegenüber dem anderen Thread geschützt.

Warum wird istOffen() innerhalb der Methoden geprüft?

Bei 14 Transaktionen könnten beide Threads außerhalb der Methoden feststellen, dass das Lager offen ist. Erst innerhalb des gemeinsamen Monitors ist die Prüfung zusammen mit der Änderung geschützt. Der erste Thread erhöht auf 15; der zweite erhält danach false und verändert nichts mehr. Der Aufruf der ebenfalls synchronisierten Methode istOffen() ist erlaubt, weil ein Thread denselben Monitor erneut erwerben darf (reentrant).

Warum wait() und notifyAll()?

Bei Bestand 0 kann der Konsument keine 10 Stück verkaufen. Er ruft wait() auf und gibt den Monitor frei. Der Produzent kann nun liefern, den Bestand erhöhen und notifyAll() aufrufen. Der Konsument kann erst nach Freigabe des Monitors weiterarbeiten und prüft die Bedingung erneut. Bei vollem Lager wartet entsprechend der Produzent auf einen Verkauf.

Die while-Schleife ist wichtig: Ein geweckter Thread muss den Monitor erneut erwerben. Inzwischen kann ein anderer Thread den Bestand verändert haben. Außerdem kann wait() ohne Signal zurückkehren. Nach dem Warten wird auch die Schließung erneut geprüft.

Was passiert bei der 15. Transaktion?

Der ausführende Thread erhöht den Zähler auf 15 und ruft notifyAll() auf. Auch ein wartender Thread wird geweckt und erkennt, dass das Lager geschlossen ist. Beide Schleifen in main enden, sobald ihre Methode false liefert. Die letzte erfolgreiche Transaktion liefert noch true; der nächste Aufruf liefert false.

Welches Ergebnis ist garantiert?

Bei diesem Test mit zwei Threads, Startbestand 100 und jeweils 10 Stück pro Transaktion sind genau 15 erfolgreiche Transaktionen möglich, sofern beide Threads normal weiterlaufen. Der Bestand bleibt zwischen 0 und 200. Die Reihenfolge der Lieferungen und Verkäufe und der Endbestand sind nicht festgelegt. join() wartet auf beide Threads und macht ihre Änderungen für main sichtbar.

Bei anderen Mengen, einem vorzeitigen Abbruch oder einem unterbrochenen Thread kann ein zusätzliches Schließsignal erforderlich sein, damit kein Thread dauerhaft wartet. Dieses Beispiel behandelt den normalen Ablauf ohne Unterbrechung.
